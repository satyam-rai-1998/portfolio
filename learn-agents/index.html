LLMs and context

Inputs and modalities

For chat, pass the customer’s text. For a receipt photo, use OCR or a vision-capable model to propose the order ID, show it back to the customer when uncertain, and look up the confirmed ID in the order service. Track extraction quality separately from the final answer.

A large language model (LLM) turns the customer’s question into a proposed next step. Give it the task, available tool schemas and relevant evidence. For A100, the model can request a lookup. The order service supplies the shipping fact.

Model selection
Compare a smaller and a larger model on the same questions. Measure correct tool selection, response time and cost per completed task. Prefer the least expensive model that meets the quality target.
Context engineering
The context window is a finite token budget shared by instructions, history, tool descriptions and results. Keep the latest order ID and cited policy passage. Summarize old turns and reserve space for the answer.
Structured outputs
Define required fields such as order_id, status and policy_source. Validate the returned object in code. A valid schema still needs a factual check against the lookup result.

State and memory

A follow-up such as “What about that other order?” needs a conversation history and a rule for resolving ambiguity. Keep working state scoped to the current user and conversation.

Working state
Store the selected order ID, retrieved passages and completed steps for this run. When two orders are in scope, ask which one the customer means.
Durable memory
Persist a preference such as language only when appropriate. Associate it with an authenticated identity, define its retention period and support deletion.
Checkpoints
Save the run ID and last completed step before pausing for human approval. On resume, reload state and recheck permissions before any external action.

Copilot Studio

  1. Create a new agent in a development environment. In its instructions, tell it to answer returns questions from the policy and use the order tool for shipping status.
  2. Upload your demo policy as a knowledge source. Ask whether an unused item is eligible ten days after delivery. Check that the citation opens the right file.
  3. Add an agent flow using “When an agent calls the flow”. Define a text input called order_id. Use a Switch to return Dispatched for A100, Processing for A101 and Unknown order for other IDs. Use “Respond to the agent” to return the status.
  4. Add the flow as a tool and describe when to call it. Test a combined order and policy question in the test pane before publishing to a test channel.

OpenAI and LangChain

With OpenAI function calling, send the model a description of the lookup function and a schema with one required string, order_id. When the response contains a function call, your application validates the arguments, runs the lookup and sends its result back with the same call ID. The model can then answer using the returned status.

Run it with LangChain and an OpenAI model

Install langchain and langchain-openai in a Python environment. Set OPENAI_API_KEY and OPENAI_MODEL locally using a model that supports tool calling. Run the script below. LangChain handles the calls between the model and your Python function.

import os
from langchain.agents import create_agent
from langchain.tools import tool

@tool
def lookup_order(order_id: str) -> str:
    """Return the status of a fictional order."""
    orders = {"A100": "Dispatched", "A101": "Processing"}
    return orders.get(order_id, "Unknown order")

agent = create_agent(
    "openai:" + os.environ["OPENAI_MODEL"],
    tools=[lookup_order],
    system_prompt="Use lookup_order for order status. Ask for a missing ID.",
)
result = agent.invoke({"messages": [
    {"role": "user", "content": "Has order A100 shipped?"}
]})
print(result["messages"][-1].content)

Check your result. Inspect the messages for a tool response containing “Dispatched”. Then change A100 to A999 and compare the tool result with the final answer.

Azure OpenAI and Microsoft Foundry

Azure OpenAI

Deploy a model with tool-calling support. To use the Responses API, configure the OpenAI client with your Azure endpoint ending in /openai/v1/, provide the deployment name in the model field and authenticate with an authorized Azure credential. Start with an A100 lookup and inspect the function arguments before connecting real data.

Microsoft Foundry Agent Service

Create a prompt agent in your Foundry project, select a deployment and add the order-support instructions. Attach the demo policy using file search where supported. Register the order lookup as a function tool and handle its execution in your application. Assign the runtime identity read access to just the intended data source.

Inspect a run. For A101, check which tool was selected, which ID it received and whether its result was Processing. For a policy question, check the retrieved passage.

Retrieval and RAG

Embeddings, vector search and reranking

An embedding represents a passage as a vector. Vector similarity can find a return policy when the customer asks about “sending something back”. Combine it with keyword search for exact product codes. Rerank the candidates against the question, keep the best supported passages and pass their document identifiers to the model.

Retrieval-augmented generation (RAG) gives the model relevant passages at answer time. Split the policy by heading, store the document title and version with each chunk, and index those chunks in a service such as Azure AI Search. Retrieve passages the caller can read and pass their text and source IDs to the model.

For “Has A100 shipped, and can I return it?”, call the order tool for the changing shipment status and retrieve the policy for the return window. Cite the policy beside the 14-day answer. If someone asks how long a refund takes, check that the agent says the demo policy does not specify a timeframe.

Tool integration and MCP

Replace the local dictionary with an order API while keeping the lookup signature. Validate the ID and verify the signed-in user owns the order on the server. Return the status and distinguish an unknown order from a service timeout.

With Model Context Protocol, a host connects an MCP client to a server that advertises tools. Expose lookup_order with a required string input, connect a compatible host, inspect its tool list and run the A100 test. Enforce authorization inside the server for every call. This lets multiple clients reuse the same lookup.

Test permissions. Give two fictional users separate orders. Request the other user’s order and check that the tool reveals no status. To add a write action such as cancellation, use a separate tool and confirm the order ID before execution.

Planning and orchestration

Give the workflow a clear start, allowed transitions and a stopping condition. For the compound order question, the order lookup and policy retrieval can run independently before their results are combined.

Routing and planning
Route status requests to the order tool and policy questions to retrieval. For mixed intent, construct a two-step plan. Ask for a missing order ID before starting the lookup.
Agent loops and handoffs
In an agent loop, the model selects a tool, observes the result and decides whether to continue. Cap iterations and elapsed time. For a specialist handoff, pass the task, evidence and expected output explicitly.
Parallel work
Run independent reads together. Wait for both before composing the answer. If the order service fails, the policy passage can still support a partial answer.

Events and reliable automation

Turn the interactive assistant into a scheduled workflow. For example, a daily trigger could collect delayed orders and send one report to the operations team.

Triggers and queues
A schedule, webhook or queue message can start a run. Validate the event and record its unique ID. Use a queue when arrivals can exceed the processing rate.
Retries and duplicate delivery
Retry transient reads with a bounded backoff. Give each report a stable delivery key. Use the provider’s idempotency support where available and reconcile uncertain sends before retrying.
Human decisions
Pause before changing an order or issuing a refund. Show the operator the order, proposed change and evidence. Record approval or rejection and revalidate the order before acting.

Evaluation and operations

Deployment and cost controls

Keep development and production connections separate. Version the prompt, tool schema and index together. Set per-run token and tool-call limits. Cache public policy passages by document version and isolate any customer-specific cache entries by identity and permission scope.

Trace one request from trigger to answer. A successful HTTP response can still contain the wrong order status, so score the business outcome as well as the execution.

Retrieval quality
Build a small labelled set with expected passages. Measure whether the right passage appeared in the top results, then check whether each answer claim follows from its citation. Add cases involving outdated or inaccessible documents.
Trust boundaries
Treat retrieved documents and tool output as untrusted data. Enforce access filters during retrieval, keep secrets server-side and restrict each tool identity to the operations it needs.
Tracing and rollout
Record the run ID, prompt version, tool calls, timings, token use and redacted errors. Track cost per resolved question and the slowest step. Compare releases against saved cases, roll out gradually and retain a rollback version.

Testing and release

  • Known order. A100 should produce Dispatched. Score the status and the policy citation separately.
  • Missing ID. Ask “Where is my order?” and check that the agent requests the ID.
  • Service outage. Simulate a timeout. Confirm the answer explains that status is unavailable and can still answer a policy question.
  • Changed policy. Update the fictional return window to 21 days. Refresh the index and verify that the answer cites the new version.

Record the question, expected facts, tool selected, latency and result. Run the cases again after changing models, instructions or connectors. Start with a test group and inspect failed traces before expanding access.
